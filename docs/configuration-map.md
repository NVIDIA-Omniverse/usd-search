Notes:
- The helm key `deepsearch.vision_endpoint` is a **backward-compatible values
  key name**; the `vision-endpoint` package itself was replaced by
  [`packages/llm-client`](../packages/llm-client/).
- Precedence everywhere: built-in default → file/YAML → environment variable.
- `view_labels` come from whatever produces the VLM metadata plugin's batch
  items; nothing in this repo sets them, and `/process/asset` takes only the
  URL and plugins, so the built-in thumbnail path sends its views unlabelled.
  Give one non-empty label per image, in image order; if the count doesn't
  match, the views are sent unlabelled with a warning (a blank label fails the
  request). This is an extension point: any upstream producer can fill them
  (e.g. a later view-classification VLM pass), and one that can't name every
  view with confidence should send no labels rather than guess, because the
  prompt treats them as fact.
- Per-role details and editing guidance: [models-and-config.md](models-and-config.md).

## Public asset URLs

By default the API speaks the same asset URLs the crawler indexed —
`s3://bucket/key` for an S3 backend, `omniverse://server/path` for Nucleus. Some
deployments would rather publish `https://` addresses. Setting
`global.url_mapping` (helm) or `USDSEARCH_URL_MAPPING_MODE` (env) makes the API
translate URLs **at its edge**: responses carry the public form, requests accept
either form. Nothing else changes — the search index, the asset graph, Redis keys
and all storage access keep using the original URLs.

Zero-config for the common case, an S3 bucket:

```bash
--set global.url_mapping.mode=s3_https
# s3://my-assets/Vehicles/car.usd  ->  https://my-assets.s3.us-west-2.amazonaws.com/Vehicles/car.usd
```

Anything else — a CDN in front of the bucket, a Nucleus web gateway, several
storage roots, publishing a subtree at a vanity root — is a list of prefix rules:

```yaml
global:
  url_mapping:
    mode: rules
    rules:
      - internal: "s3://my-assets/"
        public: "https://assets.example.com/"
      - internal: "omniverse://nucleus.internal/"
        public: "https://viewer.example.com/omni/"
```

Rules resolve longest-prefix-first, so a rule for `s3://my-assets/published/`
wins over one for `s3://my-assets/`. A rule set whose reverse mapping would be
ambiguous — two rules sharing a prefix, or one public prefix nested inside
another — is rejected at startup, because applying it half-way would silently
return the *wrong asset* rather than an error.

Applies to all three gateway-exposed services (deepsearch-api,
asset-graph-service, info-endpoint); set it once under `global`. The storage
backend listing at `GET /info/backend/storage` is deliberately left untranslated
— those roots identify infrastructure, not assets, and clients (including the
Explorer) key their auth mode off the backend's scheme.

Things worth knowing before you turn it on:

- **Requests always accept both forms**, so clients holding previously returned
  `s3://` URLs keep working. `inbound_only: true` accepts the public form without
  emitting it yet, which is a safe way to stage the rollout.
- **Percent-encoding.** A storage key may hold a space (`s3://bucket/Material
  Library/x.usd`) where an `https://` path may not, so prefix substitution alone
  emits an invalid URL. Incoming URLs are always decoded, so the escaped form
  resolves unconditionally. *Emitting* the escaped form is opt-in via
  `encode_public_paths: true` (`USDSEARCH_URL_MAPPING_ENCODE_PUBLIC_PATHS`) — it
  changes the exact string in `base_key`, dependency graphs and download
  manifests. Only `http(s)` prefixes are affected. Note the irreducible
  ambiguity: a key whose literal text contains `%20` looks like an escaped space.
- **`filter_url_regexp` is only partly translatable.** A pattern that *begins with
  a literal* public prefix is translated for you — including inside a
  whole-pattern exclusion, `~(https://assets.example.com/temp/.*)`. A pattern that
  expresses that prefix as a pattern rather than a literal is not, and will match
  nothing. Patterns without a scheme/host prefix (`.*[/]Vehicles[/].*`) work
  either way. Same for `search_path`, which is always interpreted against the
  internal path. Only the prefix is rewritten, never the pattern body, so with
  `encode_public_paths` on, a pattern copied verbatim from an emitted URL keeps
  its escapes (`/Material%20Library/.*`) and will not match the raw key — write
  that segment as it is stored, or match it loosely (`/Material.Library/.*`).
  Percent-decoding the body is not safe to do for you: `%2E` would turn a literal
  dot into "any character". See [search-filters.md](search-filters.md).
- **This changes addressing, not access.** A published `https://` URL for a
  private bucket is not fetchable without credentials; signing such links is the
  client application's job. `GET /download/asset` remains the supported way to
  get bytes out of the service.
- `usdsearch_url_mapping_unmapped_total{direction}` counts URLs that matched no
  rule — a non-zero value on a fully configured deployment means a storage root
  is missing from the rule list.
